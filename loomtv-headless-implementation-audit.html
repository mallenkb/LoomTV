Issues to address first
4

Damaged state fails open and can erase the owner.

Security & data integrityCritical issue

Evidence. apps/server/src/admin-service.js:113–124 catches every read, permission, and JSON-parse failure as an empty first-run state, then persists that replacement when a media root is configured. Public onboarding is enabled whenever no owner is visible.

Problem. A truncated or unreadable headless-admin.json is indistinguishable from a new install.

Why it matters. A storage fault can silently discard the owner boundary, overwrite recoverable state, and reopen ownership claim to the LAN.

Required fix. Treat only ENOENT as first run. Fail closed on parse/access errors, retain or quarantine the original bytes, disable onboarding, and expose a recoverable degraded state.
2

The health contract reports ready when the product is not.

System statusHigh-priority issue

Evidence. apps/server/src/server.js:59–94 always returns ok: true and status: ready; :116–121 always sends HTTP 200. The same payload declares scanning and streaming unavailable, while the admin health service reports degraded or offline.

Problem. Liveness, readiness, and capability status are collapsed into one contradictory endpoint.

Why it matters. Docker and operators can mark LoomTV healthy while its media root, database, scanner, and playback path are unusable.

Required fix. Split /livez from /readyz; return 503 with reason codes until required dependencies are available, and point container health checks at readiness.
6

A missing NAS mount can look like an empty online library.

Error preventionHigh-priority issue

Evidence. Compose defaults media to ./data/media (deploy/docker/compose.yaml:27–32), the image creates /media, the entrypoint checks only that it is a directory, and inspectMediaPath marks any directory online without a read probe.

Problem. The fallback directory masks a missing SMB/NFS mount and directly conflicts with the deployment guide’s warning not to recreate an unavailable mount as an empty directory.

Why it matters. Once scanning is enabled, this is the classic path to an apparently valid empty scan and destructive catalog reconciliation.

Required fix. Require an explicit media source, verify read and traverse access, and persist a mount sentinel or filesystem identity so “empty,” “unmounted,” and “changed device” are distinct states.
7

The LAN admin boundary is below production security standard.

SecurityHigh-priority issue

Evidence. Container and systemd examples bind plain HTTP to 0.0.0.0. The server emits no CSP, frame, content-type, or referrer protections. apps/desktop/src/main/headlessAdmin.ts:373–375 says session creation must be rate-limited, but admin-service.js:226–232 has no limiter or lockout.

Problem. Owner passwords and bearer tokens traverse the trusted LAN unencrypted, login attempts are unlimited, and the control page is frameable.

Why it matters. “Trusted LAN only” is useful scope guidance, not a sufficient control for an always-on administrative service.

Required fix. Default to loopback, require an explicit LAN opt-in or one-time bootstrap secret, document TLS/reverse-proxy configuration, add login throttling, and send a hardened header set.
8

The headless runtime is a parallel scaffold, not the media server.

Architecture & completenessHigh-priority issue

Evidence. server.js:87–93 declares desktop routes, media streaming, and library scanning false; admin-service.js:264–275 hard-fails every scan. The admin HTTP contract is separately implemented in apps/server/src/admin-page.js and apps/desktop/src/main/headlessAdmin.ts.

Problem. The deployment shell does not yet host LoomTV’s catalog, playback, profiles, or progress, and two route implementations can drift before the core is shared.

Why it matters. It cannot replace Jellyfin or even the Electron host on a NAS; further work on either adapter doubles integration risk.

Required fix. Extract one shared database/scanner/media core and one versioned admin handler, then make both Electron and apps/server compose that implementation.
9

The backup promise is materially broader than the backup.

Clarity & recoveryHigh-priority issue

Evidence. The admin page says “Protect metadata, profiles, watch progress, and scan state” (admin.html:228–230). The service copies only headless-admin.json (admin-service.js:312–324); the deployment guide’s late caveat correctly says the desktop SQLite catalog is excluded.

Problem. The primary UI can give an operator false confidence that recoverable media state has been protected.

Why it matters. Backup ambiguity is discovered at restore time, when it is too late.

Quick win. Rename this action “Back up admin settings” now, list exactly what is excluded beside the button, and do not use the broader copy until a verified SQLite snapshot-and-restore path exists.
10

Every scan exception is treated as a recoverable NAS problem.

Error diagnosisMedium-priority issue

Evidence. apps/desktop/src/main.ts:693–709 catches all folder exceptions, preserves cached rows, labels the root degraded, and continues to a completed return at :713–728.

Problem. Expected filesystem disconnects, metadata-provider failures, invariant violations, and programming defects share one recovery path and no aggregate partial-failure result.

Why it matters. Preservation is correct, but systemic defects can be hidden as ordinary root degradation and automated callers cannot distinguish complete from partial success.

Recommendation. Classify expected I/O errors, rethrow unexpected failures, and return a scan summary with failed root IDs, reason codes, preserved counts, and an explicit partial-success state.
12

The roadmap and README integration are only partially finished.

Documentation & planningMedium-priority issue

Evidence. The new README heading is inserted before the final three feature bullets, so those bullets now sit under “Headless and NAS deployment.” The roadmap is reordered, but its milestones do not name exact affected files and implemented mid-scan preservation remains listed as near-term work.

Problem. The documentation does not fully meet the requested implementation-sized roadmap or accurately separate shipped, partial, and pending work.

Why it matters. Ambiguous completion state increases duplicate work and makes acceptance reviews subjective.

Quick win. Restore the Features list, then use a milestone table with status, exact files, dependency, acceptance test, and verification evidence for each headless/NAS slice.
Needs verification
3

The safety-critical paths lack a credible verification gate.

Engineering qualityNeeds verification

Evidence. No tests were added under apps/server or deploy; apps/server/tsconfig.json:6–12 explicitly sets checkJs: false. Each folder checkpoint calls a database save that deletes and reinserts the full catalog transactionally (databaseLibraryRepository.ts:261–361).

Risk. Syntax and desktop type checks do not prove auth, corruption recovery, Docker packaging, restart behavior, mount loss, or checkpoint scalability.

Why verify. These are precisely the failure modes an unattended NAS must survive.

Verification plan. Enable JS checking or migrate the server to TypeScript; add corruption, auth, restart, offline-root, concurrent-mutation, and container tests; benchmark 100k items across multiple roots before choosing checkpoint frequency.
11

Keyboard and screen-reader behavior remains unproven.

AccessibilityNeeds verification

Evidence. The admin HTML has useful labels, visible focus styles, dialog roles, alerts, and a status toast. Its modal and mobile drawer scripts do not implement Escape handling, focus containment, focus return, or background inertness.

Risk. Keyboard focus can move behind an open surface, and dynamic health or scan changes may not be announced predictably.

Why verify. A browser is the only administration path on a headless host, so blocked keyboard access is an operational defect.

Recommendation. Add modal/drawer focus management, Escape and focus return, aria-expanded, and targeted live regions; verify with keyboard plus VoiceOver or NVDA.
Working well to preserve
1

NAS scans preserve catalog data instead of assuming absence.

Data safetyWorking well

Evidence. Unavailable roots retain cached items and scan-cache entries; mid-scan failures preserve prior items and record degraded status. Folder-boundary checkpoints are guarded by the library mutation version.

Why it works. The implementation treats an unavailable share as unknown state, not an empty source, while avoiding stale scan writes after a concurrent library mutation.

What to preserve. Keep the preservation-first reconciliation and explicit degraded state while tightening error classification and checkpoint cost.

5

The deployment posture and comparison are unusually honest.

Operations & documentationWorking well

Evidence. The container uses a non-root UID/GID, separate config/cache/media volumes, read-only media, dropped capabilities, no-new-privileges, Tini, and graceful signals. README, server docs, and the Jellyfin comparison explicitly label the boundary as health/admin-only.

Why it works. Least privilege and candid capability reporting give the next extraction phase a sound base without pretending parity has shipped.

What to preserve. Retain these defaults, the host-mounted credential model, and the comparison’s current-state wording as real services land.

What works well

Preservation and packaging point the right way.

Offline roots keep their records, and the container starts from sensible least-privilege defaults.

Primary issue

State loss can reopen administration.

A corrupt or unreadable admin file silently becomes first-run state and may be overwritten.

Recommended action

Make failure truthful before adding breadth.

Fail closed, split liveness from readiness, verify mount identity, and secure the LAN boundary.

Expected outcome

An appliance safe to leave unattended.

03 · Decision memo

Make failure safe and truthful.
Then extract the real server.

The shortest path to production is not more surface area. Protect owner state, distinguish liveness from readiness, prove the mount is the expected mount, and secure the control plane before moving the shared catalog, scanner, and playback core out of Electron.
