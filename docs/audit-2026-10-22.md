## Security findings

### S1, medium: the desktop local-image route reads any image file on disk

`apps/desktop/src/main/mediaServer.ts:1745-1759`

```ts
if (reqUrl.pathname === '/api/local-image') {
  if (!filePath || !isImageFileName(path.basename(filePath)) || !fs.existsSync(filePath)) {
```

The only checks are the file extension and existence. The sibling route `/api/thumbnail` calls `requireProfileMediaAccess(filePath)` at `mediaServer.ts:1775` before streaming. The local-image branch has no such call, and no library-root containment either.

The route needs only the loopback access token, which the renderer receives over IPC (`ipcHandlers.ts:976-979`). Any renderer-side code can therefore read any `.png`, `.jpg`, `.webp` or `.avif` file the user can read, including images outside the library roots.

Fix: apply `requireProfileMediaAccess(filePath)` the way the thumbnail route does, or resolve through `resolveLocalResource()` in `resourceRegistry.ts:128-164`, which enforces containment with `realpath`.

### S2, medium: the admin backup endpoint writes a credential dump to any directory

`apps/server/src/admin-page.js:441-452`, `apps/server/src/admin-service.js:2355-2363`

The public API checks the backup destination before writing:

```js
// public-api.js:1919
if (destination && typeof service.isBackupPathAllowed === 'function' && !service.isBackupPathAllowed(destination)) {
  throw requestError(403, 'backup_path_forbidden', ...
```

`isBackupPathAllowed` (`admin-service.js:2327-2330`) confines the path to `<dataDir>/backups`. The `/api/admin/backup` POST route never calls it. `startBackup` resolves the caller's path and `writeBackupFile` (`admin-service.js:833-855`) creates the directory and writes the file with mode 0600.

The envelope contains every account's `salt` and `hash`, session token hashes and device credential hashes (`admin-service.js:291-308`). Any account holding the `admin` role can plant that file in a directory it chooses, including a synced folder or a web-served path.

Fix: call `isBackupPathAllowed(destination)` in the admin route the same way the public route does.

### S3, medium: the admin library routes leak absolute server paths to the viewer role

`apps/server/src/admin-page.js:373-377` and `:396-399` return `listLibraryRoots` and `listLibraryItems` to any principal with `library.read`. The `viewer` role holds that permission by default (`auth-policy.js:38`).

`rootView` (`admin-service.js:1853-1858`) spreads the root record, which includes `path`. `listLibraryItems` (`admin-service.js:2054-2090`) spreads each scanner record, which includes `path` and `subtitleSidecars[].path`.

The project already found this exact leak and fixed it elsewhere. `media-service.js:76-80` says so in a comment:

> The versioned API strips `path` from every catalog DTO. This legacy listing route did not, so any account with library.read, a viewer by default, could read absolute server paths for the whole library.

`redactedLibraryItem` (`media-service.js:82-106`) and `publicLibraryItem` (`public-api.js:269-303`) both strip it. The admin routes were never given the same treatment, so the leak survives to the lowest-privilege account role and to any paired device holding `library.read`.

Fix: redact `path` in the admin listing DTOs the same way.

### S4, medium: the desktop stores its encryption key next to the ciphertext

`apps/desktop/src/main/localSecretStorage.ts:11-49`

The AES-256-GCM key lives at `<userData>/loomtv-local-secrets.key`, mode 0600. The encrypted database and the encrypted settings live in the same `userData` directory. One directory read gets the key and every stored API key, the LAN HMAC secret, the LAN share token and every add-on credential.

`safeStorage` is imported at line 1 but used only to read legacy ciphertext (`:66-67`). The app actively migrates away from it (`database.ts:314-317` sets `needsMigration: true` and re-encrypts with the local file key). That is a downgrade from the OS keychain.

The file hygiene is good. The key path rejects symlinks and files owned by another OS user (`:24-28`), and the write uses mode 0600.

Fix: keep using `safeStorage` where the OS offers it, or at minimum stop migrating away from it.

### S5, medium: the legacy plaintext settings file survives the migration

`apps/desktop/src/main/settings.ts:14` and `:280`

`saveSettings` writes only to the database. The legacy `settings.json` is read for migration and never removed. The only code that deletes it is `clearAppData` (`main.ts:643-649`).

So on any install upgraded from an older release, `settings.json` still holds `omdbApiKey`, `tmdbApiKey`, `metadataApiKeys`, `localNetworkHmacSecret` and `localNetworkShareToken` in plaintext, next to the encrypted copy. That defeats S4 for exactly the users who upgraded.

Fix: delete `settings.json` after a successful migration.

### S6, high: the first owner claim is unauthenticated by default

`apps/server/src/cli.js:144-146`, `apps/server/src/secure-bootstrap.js:113-117`, `apps/server/src/admin-service.js:1550-1552`

```js
const requireBootstrapSecret = cliValues.requirebootstrapsecret !== undefined
  ? cliValues.requirebootstrapsecret
  : ['1', 'true', 'yes'].includes((readEnvironmentValue('REQUIRE_BOOTSTRAP_SECRET', ...) || '').toLowerCase());
```

The CLI default is false. `server.js:143` and `admin-page.js:262` default to true when their option is omitted, but the CLI always passes the false value into both. `secure-bootstrap.js` returns early without generating a secret file when the flag is false. `createOwner` only calls `bootstrapSecurity.authorize()` when it is true, so `POST /api/v1/setup/owner`, `POST /api/v1/auth/owner` and `POST /api/admin/onboarding/owner` accept an unauthenticated owner claim on a fresh install.

Neither `deploy/docker/compose.yaml` nor `deploy/systemd/loomtv.env.example` sets `REQUIRE_BOOTSTRAP_SECRET`. The server README's option table (`apps/server/README.md:53-54`) lists the bootstrap secret file and value with a default of "generated when no owner exists", which is only true when the flag is on. The prose section below it does describe the flag correctly, but the flag is missing from the table and no deployment enables it.

In the documented NAS deployment, where a reverse proxy fronts the server, the first owner claim is reachable by anyone who can reach the proxy until someone claims it. That is at least the LAN, and the internet if the proxy is exposed.

Fix: default the flag to true for non-loopback binds, or set it in both deployment configs and add the flag to the option table.

### Controls verified as correct

These came up during the review and hold up. Recording them so a future audit does not re-check them.

Electron. All four `BrowserWindow` sites set `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`. No `nodeIntegration: true`, `webviewTag`, `allowRunningInsecureContent` or `experimentalFeatures` anywhere in `apps/desktop/src`. Permissions are default-deny through `setPermissionRequestHandler`, `setPermissionCheckHandler` and `setDevicePermissionHandler` (`permissionPolicy.ts:26-33`), installed on every session via `app.on('session-created')`. Navigation guards block `will-navigate`, `will-redirect` and `will-frame-navigate` unless the URL matches the immutable app identity captured at window creation (`trustedIpcSender.ts:28-50`), with a three-host allowlist for embedded video. No window can open another window. The packaged CSP has `script-src 'self' file:` with no `unsafe-inline` or `unsafe-eval`. Every `ipcMain.handle` goes through one of three wrappers that call `isTrustedSender` before parsing args with zod, and there are no `ipcMain.on` handlers at all. Path-taking handlers call `authorizeMediaPath`, which requires an exact match against a library-indexed path, so traversal cannot escape it. No `eval`, no `new Function`, no `shell: true`, no string-built shell commands. All child processes use argv arrays. The auto-updater pins the feed to a hard-coded repo, verifies a sha512 checksum, runs `codesign --verify --deep --strict`, and requires matching bundle and team identifiers. Fuses are set in `forge.config.ts:536-544`.

Outbound requests. `safeFetch.ts:140-159` requires HTTPS, enforces a host allowlist, rejects private and reserved IPv4 and non-global IPv6, then pins the validated address into the request to close the DNS-rebinding window. Redirects are revalidated at each hop and sensitive headers are stripped cross-origin. The Stremio adapter enforces its own HTTPS-only, no-credentials, no-private-range rules with `redirect: 'error'`.

Plugins. No third-party code is ever executed. The protocol is declaration-only and host-mediated. The quarantine state cannot be cleared by any API. Torrent and peer-to-peer refusal is real: `inspectP2pSource` catches magnet links, `.torrent` URLs, `infoHash`, `fileIdx` and peer `sources`, and `normalizeStreamCandidate` marks them `playableByLoom: false` with reason `P2P_UNSUPPORTED`. The README claim on line 120 is accurate.

Server. Session tokens are 32 random bytes stored only as a SHA-256 hash and compared with `timingSafeEqual`. Passwords use scrypt with a random salt. Login timing does not distinguish a missing user, since scrypt still runs against a fixed salt. Session ids are never accepted from the client, so there is no session-fixation path. The session cookie is `__Host-loomtv_session`, `HttpOnly; Secure; SameSite=Strict`. CSRF uses a same-origin check plus a constant-time double-submit comparison on every non-GET cookie-authenticated request. The server never sends `Access-Control-Allow-Origin`. All SQL uses prepared statements with bound parameters; the only interpolated fragments are internal constants. The path guard (`media-path-guard.js`) canonicalizes, compares with segment boundaries, opens with `O_NOFOLLOW` and re-checks identity after the open. Scrypt is admission-controlled with a queue and a 429. No log statement prints a password, PIN, token or API key, and audit details are filtered for secret-shaped keys.
